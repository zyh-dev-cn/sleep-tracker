# 简历与面试材料

> 仓库：https://github.com/zyh-dev-cn/sleep-tracker
> 技术栈：Java 17 / Spring Boot 3 / MyBatis-Plus / MySQL / JWT / DeepSeek API / Vue 3 / ECharts

## 一、简历项目描述（可直接粘贴）

**睡眠记录与 AI 分析平台**（个人项目｜2026.11）

独立完成的全栈 Web 应用，支持睡眠数据记录、统计可视化，并接入大模型生成个性化改善建议。

- 后端基于 Spring Boot 3 + MyBatis-Plus + MySQL 实现分层架构（Controller / Service / Mapper），提供 8 个 REST 接口，集成 springdoc 生成在线接口文档；前端使用 Vue 3 + ECharts 实现单页应用与趋势图。
- 基于 JWT 实现无状态鉴权与多用户数据隔离：拦截器统一验签并通过 ThreadLocal 传递用户上下文，所有查询附带 `user_id` 条件，修改/删除前校验记录归属，防止水平越权（IDOR）。
- 接入 DeepSeek 大模型生成睡眠建议：先将统计指标与近期记录聚合成自然语言摘要再调用模型，降低 token 消耗；以「用户 + 摘要哈希」为 key 实现本地 LRU 缓存（6 小时过期），数据未变时零成本返回。
- 处理跨天时间与统计口径问题：入睡跨午夜导致时长为负，统一 +24 小时修正；通过单元测试发现并修复「凌晨入睡被误判为最早」的比较缺陷，补充 13 个 JUnit 用例覆盖时间计算、JWT 校验与统计聚合。

## 二、项目难点（面试口述版，1 分钟）

难点不在功能，而在两个"看起来对、实际错"的地方：

1. **跨天时间**。入睡时间常在午夜后，`Duration.between` 会得到负数。所有时长计算统一对负值加 24 小时。
2. **统计口径**。最早入睡时间不能直接比较 `LocalTime`——凌晨 00:10 在时钟上小于 23:20，但实际睡得更晚。我把它映射到"夜晚时间轴"（中午 12 点前 +24 小时）再比较。这个 bug 是写单元测试时用边界数据发现的，页面上看不出来。

另外就是 AI 的成本控制：不把原始数据丢给模型，先聚合成摘要，再对摘要做哈希缓存。

## 三、高频面试问答

**Q1：为什么用 JWT 而不是 Session？**

JWT 是无状态的，服务端不存会话，天然支持多实例部署，不需要 Redis 做 session 共享；代价是签发后无法主动作废。Session 的好处是服务端可控、能随时踢人。

**Q2：用户改密码后旧 token 还能用，怎么解决？**

现在的实现里能用到过期（72 小时）。改进方案有两个：一是用户表加 `tokenVersion` 字段，签发时写进 payload，验签时比对；二是维护 Redis 黑名单存未过期的失效 token。

**Q3：ThreadLocal 为什么必须 remove？**

Tomcat 用线程池复用线程。不清除的话，下一个请求可能读到上一个请求残留的 userId，导致数据串号；在长期运行的线程池里还会造成内存泄漏。所以放在 `afterCompletion` 里清理，保证异常时也执行。

**Q4：拦截器和过滤器（Filter）的区别？**

Filter 属于 Servlet 规范，在进入 Spring MVC 之前执行，拿不到 Controller 方法信息；Interceptor 是 Spring MVC 的，能拿到 HandlerMethod，适合做鉴权。AOP 更细，能切到方法内部。

**Q5：为什么密码用 BCrypt 而不是 MD5？**

MD5 太快且无盐，能被彩虹表反查、能暴力枚举；BCrypt 自带随机盐、计算慢（强度可调），同样密码每次加密结果都不同，只能 `matches` 比对，不能 `encode` 后直接比较。

**Q6：怎么防止用户改 URL 里的 id 访问别人的数据？**

两层：查询时 SQL 强制带 `user_id` 条件；修改和删除前先按 id 查出来，校验 `userId` 是否等于当前登录用户，不等就返回失败。这就是 OWASP 里的水平越权（IDOR）。

**Q7：缓存 key 为什么用摘要哈希？**

摘要由统计值和最近 7 条明细拼接而成，任何一条记录变化都会让哈希变化，天然实现"数据变了就失效"，不需要额外维护版本号或更新时间戳。同时 key 里带 userId，避免不同用户串结果。

**Q8：缓存会不会击穿/雪崩？**

当前是单机 LRU + 固定 6 小时过期，规模小够用。如果要上线多实例，应该换成 Redis，并对同一 key 加互斥锁避免并发穿透，过期时间加随机偏移避免同时失效。

**Q9：AI 接口超时或报错怎么处理？**

统一 try-catch，返回可读的提示（未配置 Key、余额不足、网络异常），失败结果不写入缓存，避免把错误固化。生产环境还应加超时时间、重试和降级（比如返回规则引擎生成的模板建议）。

**Q10：数据量到百万级怎么优化？**

建索引（`user_id + bed_time` 联合索引）、分页查询、统计改为 SQL 聚合而不是全量拉到内存算 Stream、AI 摘要只取聚合值和最近 N 条。
